title: 'SSO'
description: 'Manage SAML and OIDC providers for your Carbon org.'
---

Enterprise orgs can register SAML or OIDC identity providers through
the admin-only SSO management routes. Configuration is stored on the
organization record and drives the dashboard sign-in flow.

## Sign-in flow

1. User visits `https://<dashboard>/sign-in` and types their email.
2. The sign-in page calls `GET /api/auth/sso/discovery?email=<addr>`,
   which returns a provider match if the email's domain equals the
   `emailDomain` on a registered SSO provider.
3. On a match the sign-in page swaps the password button for
   **Sign in with <ProviderName>**, which hits
   `GET /api/auth/sso/login?providerId=<id>&next=<path>`.
4. That endpoint redirects to the provider's OIDC authorize URL.
5. On the return trip, `GET /api/auth/sso/callback?code=&state=`
   exchanges the code for an `id_token`, extracts the email claim,
   upserts the user in the shared Postgres, and sets the Better Auth
   session cookie.

### Callback URL to register at your IdP

```
https://<dashboard-host>/api/auth/sso/callback
```

Enterprise-provisioned deep-links can skip the discovery step by
appending `?sso=<providerId>` to `/sign-in` — the page bounces to
`/api/auth/sso/login` immediately.

<Note>
  SAML is planned; today the shim only implements OIDC. The management
  routes still accept `type: 'saml'` for forward-compatible storage.
  Registering a SAML provider today lets you configure IdPs ahead of
  the release, but the sign-in flow will 501 for SAML providers until
  `@better-auth/plugin-sso` ships and this shim is retired.
</Note>

## Routes

All routes require an `admin`-scoped API key and an Enterprise org — a
non-Enterprise org gets `403 CARBON_FORBIDDEN` with an actionable
message rather than a silent success.

| Method | Path                        | Purpose                        |
| ------ | --------------------------- | ------------------------------ |
| GET    | `/v1/sso/providers`         | List configured providers      |
| POST   | `/v1/sso/providers`         | Register a SAML or OIDC provider |
| DELETE | `/v1/sso/providers/:id`     | Remove a provider              |

## Register a SAML provider

```bash
curl -X POST https://api.carbon.dev/v1/sso/providers \
  -H "x-carbon-key: ck_live_admin_…" \
  -H "content-type: application/json" \
  -d '{
    "type": "saml",
    "name": "Okta (Acme)",
    "entityId": "https://acme.okta.com/…",
    "ssoUrl":   "https://acme.okta.com/app/…/sso/saml",
    "certificate": "-----BEGIN CERTIFICATE-----\nMIIC…\n-----END CERTIFICATE-----",
    "emailDomain": "acme.example"
  }'
```

## Register an OIDC provider

```bash
curl -X POST https://api.carbon.dev/v1/sso/providers \
  -H "x-carbon-key: ck_live_admin_…" \
  -H "content-type: application/json" \
  -d '{
    "type": "oidc",
    "name": "Google Workspace (Acme)",
    "issuer":       "https://accounts.google.com",
    "clientId":     "…apps.googleusercontent.com",
    "clientSecret": "GOCSPX-…",
    "emailDomain":  "acme.example"
  }'
```

## Audit trail

Every SSO change writes an audit event (`sso_provider.created` /
`sso_provider.deleted`) so it shows up in `carbon activity` and in the
[compliance export](/security/compliance-export) `events` / `audit`
buckets.
